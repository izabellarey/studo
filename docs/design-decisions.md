This document records the most important architecture decisions of STudo in a compact decision-record format: the context that led to the decision, the decision itself and its consequences, including the trade-offs the team accepted.

## 1. One REST API for all clients

**Context.** The product has two very different clients, a full-featured web interface for planners and a mobile app for teachers and students, built by separate sub-teams under time pressure.

**Decision.** Both clients use the same REST API of one backend. The interface contract (endpoints and DTOs) was agreed in the design phase, before implementation. The Android app talks directly to the backend, not through the web client.

**Consequences.** Web and Android stay consistent because they read the same data with the same security rules, and the sub-teams could work in parallel against the agreed contract. The price is that contract changes need coordination across three teams, and that the API has to serve different views of the same data, which is handled with specialised DTOs.

## 2. Thin, read-only Android client

**Context.** Planners do all configuration and planning. Teachers and students only need to see timetables, changes and room schedules.

**Decision.** The Android app contains no business logic that modifies timetable data. It only fetches and presents.

**Consequences.** The app is simple, quick to build and easy to test, and the entire business logic stays in one place. In exchange, features that would need write access from the app (for example teachers accepting a substitution) require API and security extensions.

## 3. Layered backend with DTOs separate from entities

**Context.** The domain model has many relationships (lessons, teachers, rooms, events, changes, rules). Serialising JPA entities directly would expose internal structure and cause lazy-loading errors and infinite recursion in bidirectional associations.

**Decision.** The backend is organised in controllers, services and repositories. Controllers only map requests to services. Services contain the business logic. Repositories are Spring Data interfaces. The API exchanges DTOs only; entities never leave the service layer.

**Consequences.** The external API can evolve independently from the database model, and internal fields (for example password hashes) cannot leak by accident. The cost is mapping code and a larger number of classes, which the team reduced by organising DTOs by feature and reusing them across controllers where it made sense.

## 4. Stateless JWT authentication with central authorisation

**Context.** Two client types, web and Android, need authentication that works without server-side sessions.

**Decision.** Users log in with username and password and receive a signed JSON Web Token carrying username and role. A filter validates the token on every request. Authorisation rules are defined centrally in the Spring Security filter chain by role instead of being spread across individual methods. Controllers derive the user's identity from the authenticated principal, never from a client-supplied ID.

**Consequences.** The backend scales without session state, and security rules are visible in one place. The backend is the only trusted authority. Clients hide controls for usability only. Tokens cannot be revoked individually before they expire, which was acceptable for this scope.

## 5. Manual account management without e-mail flows

**Context.** Schools create accounts for their students and staff themselves, and the customer explicitly required that no e-mail based process is involved.

**Decision.** Usernames are generated by the system in the form `firstname-lastname`. An initial planner account ships with the product, and planners create all other accounts. Planners change their own passwords with the old password. Teachers and students get new passwords from a planner, which forces a password change on the next login.

**Consequences.** The system is independent of mail infrastructure and fits the school's processes. The downside is an administrative burden on planners and no self-service password recovery for teachers and students.

## 6. Embedded H2 database with schema from entities

**Context.** The project was first prepared with MySQL. The supervisors recommended a simpler setup for a single-school product delivered in four weeks.

**Decision.** The backend embeds an H2 database with file persistence. The schema is derived from the JPA entities by Hibernate, and a seed file creates the demo school. No separate migration tool is used.

**Consequences.** Installation shrinks to two containers and there is no database server to operate. Resetting the system for demos is trivial. For a larger production setup, the team would introduce a client/server database and a migration tool such as Flyway, which the JPA-based persistence layer would allow with little change.

## 7. Timefold Solver for timetable generation

**Context.** Timetable generation is a combinatorial optimisation problem with many interacting rules. Writing a custom search algorithm with a solid scoring model within four weeks was a considerable risk.

**Decision.** The team uses the open-source Timefold Solver for the search and the score mechanics. STudo contributes the planning model and the domain constraints. The result is a list of scored variants rather than a single plan.

**Consequences.** The team focused on modelling and rules instead of search infrastructure and could add or change constraints declaratively. Generation is time-boxed and takes several minutes for a whole school, so the user interface must handle a long-running operation. The result is good rather than provably optimal.

## 8. Hard and soft constraints as configurable data

**Context.** Rules differ by federal state and school, and schools adapt them over time.

**Decision.** Maximum workloads, break rules, block rules and mandatory subjects are stored as data entities with an active flag, a hardness (hard or soft) and a weight. Break rules and maximum workloads come preconfigured from the federal state, while subject quotas and block preferences are edited by planners. Grade levels carry a planning priority that decides which grade levels are served first.

**Consequences.** The rule set can be changed without a code change and the planner stays in control. The solver must interpret the stored rules generically, which is more elaborate than hard-coding them.

## 9. Assistant suggestions instead of full automatic rescheduling

**Context.** Substitutions have to be made quickly and under pressure, but they also involve human judgement, such as who is willing or suitable.

**Decision.** For every open change the system proposes only conflict-free substitute teachers or alternative rooms and lets the planner decide. The planner confirms the change explicitly.

**Consequences.** Planners cannot accidentally create new conflicts and keep full control over the outcome. The cost is a manual confirmation step per change. A fully automatic mode remains a possible later extension.

## 10. Containerised deployment with Docker Compose

**Context.** The system must be reproducible on a university-provided server and easy to demonstrate.

**Decision.** Backend (with embedded database) and web frontend run in separate containers orchestrated by Docker Compose. Configuration is passed through environment variables.

**Consequences.** Setup is one command and works identically on every machine. The web frontend runs on a different origin than the API, so the backend needs an explicit CORS configuration. The Android app is built separately and points to the server through a configurable address.

## 11. Single-school installation

**Context.** The customer's requirement is to serve one school.

**Decision.** The system is not multi-tenant. The schema has no school identifier, and one installation equals one school.

**Consequences.** The model and all queries stay simple. Supporting several schools in one installation would require a tenant concept in the schema, the security layer and every repository query.
